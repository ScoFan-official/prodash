## 前置条件

- 宿主机（运行后端的那台笔记本）已安装 **dws CLI** 并已登录，个人 token 有效（可先执行 `dws profile list` 确认）。
- Windows 下 dws 常以 `.cmd` / `.bat` shim 分发：Node `execFile` 直调会报 `ENOENT`，需在 `.env` 里配 `DWS_BIN` + `DWS_SCRIPT`（见「注意事项」）。
- 后端代码已有启动警告：`PUBLISHER=dws` 但 `DINGTALK_WIKI_WS_ID` 为空时，启动会打印 warn（见「步骤⑤」）。

## Dify 工作流应用变量配置

日报正文由 Dify 工作流应用生成，**开始节点输入变量与结束节点输出变量需按 README「Dify 工作流变量契约」配置**（字段名以代码 `server/services/reportService.js` 的 `buildDifyInputs` 为准）：[README.md](../../README.md#dify-工作流变量契约)。

- 用 dify-agent 创建 / 更新「日报助手」工作流应用后，在 Dify 控制台按契约核对：
  - **开始节点**：配置 7 个输入变量 `report_date` / `completed_tasks` / `pending_tasks` / `extra_work` / `risks` / `tomorrow_plan` / `time_summary`，全部为 string 类型；
  - **结束节点**：输出变量配置为 `report`（string，日报正文）。
- **与 0.2.x 阶段旧工作流的差异**（沿用旧工作流需更新，否则 Dify 会因缺变量 / 取不到 `report` 报错）：
  - **新增 `time_summary`** 输入变量（当日双轨总时长，JSON 对象字符串）；
  - **`completed_tasks` / `pending_tasks` 数组项新增 `humanMs` / `agentMs` 字段**（该任务当日人工 / Agent 时长）；
  - `extra_work` 收窄为仅 `{ temporaryWork, meetings }`，`risks`、`tomorrow_plan` 拆分为独立输入变量。

## 步骤

### ① 创建或确认知识库空间（实测命令）

```bash
# 列出已有空间（确认是否可复用）
dws wiki space list --format json

# 没有可用的空间则新建（--name / --desc 按需修改）
dws wiki space create --name "AI日报测试" --desc "Prodash 日报发布演示空间" --format json
```

返回字段含 `workspaceId`，例如：

```json
{ "workspaceId": "o5WXM7eZqwEnoGwO" }
```

从中提取 **WS_ID** = `workspaceId`。上例为本次实测值，**请替换为你自己的返回值**。

### ② 在知识库内创建「日报」文件夹（实测命令）

```bash
dws wiki node create --workspace <WS_ID> --name "日报" --type folder --format json
```

返回字段含 `nodeId`，例如：

```json
{ "nodeId": "2Amq4vjg89gzAjqjim722daLV3kdP0wQ" }
```

从中提取 **FOLDER_ID** = 该 folder 节点的 `nodeId`（上例为本次实测值，请替换为你自己的返回值）。

> **注意**：`dws doc create --folder` 参数应传 **folder 节点的 `nodeId`**，不是返回对象里可能出现的 `folderId` 字段——两者不同，传错会导致文档建错位置或失败。

### ③ 提取 WS_ID 与 FOLDER_ID

记录上两步实际返回中的两个 ID（WS_ID 来自 `workspaceId`、FOLDER_ID 来自 folder 的 `nodeId`）。**ID 一律来自命令返回，严禁编造**；建议先保存在本地草稿，供下一步写入 `.env`。

### ④ 写入 .env

在项目根目录 `.env`（已被 .gitignore 忽略，不会提交）中写入：

```env
DINGTALK_WIKI_WS_ID=<第①步提取的 WS_ID>
DINGTALK_WIKI_FOLDER_ID=<第②步提取的 FOLDER_ID>
PUBLISHER=dws
```

Windows 下 dws 为 `.cmd` / `.bat` shim 时，另加 `DWS_BIN` + `DWS_SCRIPT`（见「注意事项」）。

### ⑤ 启动校验

- 后端启动时若 `PUBLISHER=dws` 且 `DINGTALK_WIKI_WS_ID` 为空，会打印警告：
  `[prodash-server] [warn] PUBLISHER=dws 但 DINGTALK_WIKI_WS_ID 为空：创建日报文档会失败并标记 publish_failed ...`
  配置后此警告应消失。
- 可用 `dws drive list --workspace <WS_ID> --format json` 验证 WS_ID 有效（能列出空间内内容即有效）。

### ⑥ 首次真实发布验证（实测结果）

1. 启动 MySQL + 后端：
   ```bash
   docker compose up -d
   npm run server
   ```
2. 手动触发生成（`date` 填当天）：
   ```bash
   curl.exe -X POST http://127.0.0.1:8787/api/reports/generate ^
     -H "Content-Type: application/json" ^
     -d "{\"date\":\"YYYY-MM-DD\"}"
   ```
   > Windows PowerShell 下 `curl` 是 `Invoke-WebRequest` 别名，请用 `curl.exe`。
3. 检查结果（本次实测）：
   - report `status=published`，`docUrl` 为真实 alidocs 链接，`docNodeId` 为真实知识库节点；
   - 钉钉知识库「日报」板块出现「日报 YYYY-MM-DD」文档。
4. **覆盖验证（实测通过）**：再次 generate（或机制 b 补充内容触发重生成）→ **同一 docNodeId 被更新覆盖**，不会新建文档。
5. **同名冲突提示**：文档名为 `日报 YYYY-MM-DD`，若知识库中已有同名文档，钉钉会自动加 `(1)` 后缀（如「日报 YYYY-MM-DD (1)」），可用 `dws doc rename` 纠正。
6. **URL 字段位置**：`dws doc create` 的文档 URL 实际位于输出 `serverResponse.docUrl`，代码 `extractDwsResult` 已兼容解析该位置。

## 注意事项

- **Windows .cmd shim 方案（实测验证）**：dws 若以 `.cmd` / `.bat` 分发，Node `execFile` 直调会报 `ENOENT`。实测解决方案：`.env` 里配置
  ```
  DWS_BIN=<node.exe 绝对路径>
  DWS_SCRIPT=<dws CLI 的 JS 入口绝对路径，如 ...\node_modules\dingtalk-workspace-cli\bin\dws.js>
  ```
  发布器检测到 `DWS_SCRIPT` 时按 `node dws.js <args>` 调用（见 `server/publishers/index.js`）。
- 发布失败时 report 停在 `publish_failed`，前端提供补发按钮；dws token 过期属 demo 接受风险，不自动刷新（决策清单 §五）。
