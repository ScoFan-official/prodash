## 一、产品定位（含改口声明）

v1.0.0 的定位是 **能跑通全链路的演示原型**，以"生产环境的姿势"编写（目录结构、接口抽象、`.env` 分离），但明确承认 **demo 特权**：

- 不实现降级/重试/监控/多租户；
- 钉钉侧走**个人版通道（dws）**，不做企业应用；
- 生产化改版**另行立项**。

> 本文档每个决策点都预留「生产化线索」字段，供后续 v1.x 生产化时定位改造点。这是本清单最有价值的部分。

## 二、目标架构

钉钉群应用整体推到 v1.x（v1.0.0 不做免登、不做群应用嵌入）。v1.0.0 的真实形态：

```
浏览器直连 localhost（后端托管的 H5，同域，无 CORS）
    ↓ HTTP API（无登录，单用户 demo）
Node 后端（跑在笔记本宿主）
    ├── MySQL（Docker 容器 + 数据卷）      ← 数据源 of truth
    ├── Dify Workflow API（公司私有化，远程）← 只产出日报文本
    └── 发布器接口 publishReport(...)       ← 接口抽象（生产化线索①）
            └── DwsCliPublisher（宿主 dws CLI，个人 token）
                    ↓
        钉钉知识库「日报」板块（doc create / update）
```

| 组件 | v1.0.0 位置 | 说明 |
|---|---|---|
| 前端 H5 | Node 后端托管（同域） | GitHub Pages 退役，只是一次尝试，不再维护 |
| Node 后端 | 笔记本宿主（`npm run dev`） | CRUD + 调度 + 发布 |
| MySQL | Docker 容器 + 数据卷 | 数据源 of truth，前端直连 API 读写 |
| Dify | 公司私有化（远程） | 只产出日报文本（用户已确认"Dify 只产出文本"） |
| dify-agent MCP | 笔记本（构建期工具） | 用户级权限自动创建 Dify 应用，非运行时组件 |
| dws CLI | 宿主（个人 token） | 发布到知识库的唯一通道 |

## 四、口径与调度（已钉死）

| 决策点 | 结论 |
|---|---|
| 数据源 | **DB 为主**，前端直连 API；localStorage 废弃并**清零**（存量数据不迁移，demo 从新开始） |
| 完成口径 | `completedAt ∈ [服务器本地当天 00:00, 次日 00:00)`，"今日完成"按完成时刻归属（跨日切分顺带解决） |
| 删除语义 | **软删除保留**；是否入日报由**个人端开关**控制（默认关） |
| 触发时刻 | 默认 **21:00**（`REPORT_CRON` 可配），**仅决定自动生成的调度时刻**，不参与"今日完成"归属判定 |
| 跨日边界 | `completedAt ∈ [服务器本地当天 00:00, 次日 00:00)`（**服务器本地时区**，非 UTC 墙钟） |
| 文档命名 | `日报 YYYY-MM-DD`，一天一个固定 nodeId，**重生成=更新覆盖**，不新建 |
| 补充内容机制 | **(b)**：固定时刻先自动生成 → 用户当天后填补充内容 → 检测到变更自动重生成覆盖当天文档 |

> 口径说明：21:00 只是调度时刻，不是日界。21:00-24:00 完成的任务仍归属"今日"；调度先生成后，用户若在当天补充内容，机制 (b) 会带最新数据重生成并覆盖当天文档，该批任务随之进入"今日完成"。

## 五、dws 集成（demo 关键风险区）

### 接法：方案甲 + 方案丙（已选定）

- **方案甲**：后端跑宿主，MySQL 进 Docker。避免 Windows/Linux 二进制不通用、token 目录挂载、隔离等问题。
- **方案丙**：`publishReport({date, title, content}) → {docUrl}` 接口抽象，当前实现 `DwsCliPublisher`（shell 调 `dws doc create/update`）。

### token 生命周期（demo 接受的风险）

- dws profile 有 `expiresAt / refreshExpAt`，会过期。18:00（或 21:00）触发时 token 可能失效。
- demo 兜底：发布失败 → report 保持 `draft / publish_failed` → 前端提供**补发按钮**。不实现自动刷新。
- 生产化线索④：生产化改为企业应用 AppKey/Secret，server-to-server，无个人 token 生命周期问题。

### 待确认（阻塞实现前需现场核实）

- dws 认证/profile 目录位置（疑似 `~/.dws/`，以 `dws profile list` 实际安装为准）；
- 若日后全容器化，需要 dws **Linux 版**二进制（v1.0.0 不需要）。

## 六、钉钉知识库预配（一次性）

1. 用 dws 创建（或复用）知识库空间 + 「日报」文件夹，**从命令返回提取** WS_ID 与 FOLDER_ID（ID 严禁编造）。
2. 写入 `.env`（已被 .gitignore 忽略）：
   ```
   DINGTALK_WIKI_WS_ID=...
   DINGTALK_WIKI_FOLDER_ID=...
   ```
3. 写 `docs/provisioning/钉钉知识库初始化.md`，记录命令原文与返回 ID（生产化 replays 线索⑤）。
4. **后端启动校验**：用 `dws drive list --workspace` 探测 ID 有效，无效即 fail-fast 报错。

## 九、v1.0.0 验收标准（演示全链路）

1. 笔记本启动 Docker（MySQL）+ 后端 + 前端，浏览器打开 localhost 正常使用 prodash；
2. 新建任务、开双轨计时、勾选完成若干条；
3. 手动触发生成（或等到 21:00 自动）→ 后端调 Dify 产出日报文本；
4. 日报落库（status=published），**钉钉知识库「日报」板块出现当日文档**；
5. 前端日报历史列表可看到当天日报与 doc_url，点击可打开；
6. 填补充内容 → 自动重生成 → 同一文档内容被覆盖更新；
7. 软删除任务按开关选择是否入日报；
8. 模拟 token 失效 → report 停在 publish_failed → 点补发成功。
