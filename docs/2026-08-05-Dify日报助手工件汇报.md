## 一、项目背景

Prodash 是一个以 React + Vite 为技术栈的个人效率网页应用（GitHub Pages 部署），已完成「四象限待办」功能：

- 深色主题、响应式布局
- 艾森豪威尔四象限待办（双视图：列表 + 四象限）
- 浏览器 localStorage 持久化
- 无后端、无账号、无数据库

公司环境：

- 内部办公使用钉钉
- 公司私有化部署了 Dify
- 实习生有 Dify 账号，但无法获取管理权限（Admin API Key）

---

## 二、需求探索

用户希望将 Dify 与 Prodash 结合，功能集成到钉钉。候选场景包括：

1. **钉钉 AI 待办助手**：在钉钉私聊/群聊中发送一句话，Dify 解析成待办并同步到 prodash
2. **工作日报助手**：Dify 汇总 prodash 中的任务完成情况，生成日报并发送到钉钉 ✅ **选定**
3. **钉钉消息转任务**：用户转发钉钉消息给机器人，AI 提取任务、负责人、截止时间并写入 prodash

经Ai对话讨论，三个场景后续均会实现，本次优先实现 **工作日报助手**。

---

## 三、设计方案

### 功能需求

- 日报内容来源：prodash 当天的待办数据 + 用户手动补充的工作内容（临时工作、会议、问题、明日计划）
- 触发方式：支持定时自动生成 + 手动点击生成
- 发送对象：发送到开发者本人的钉钉私聊（当前阶段）
- 日报格式：固定结构 + AI 润色（今日完成 / 进行中 / 补充工作 / 问题与风险 / 明日计划）

### 权限约束

- **Dify**：用户只能创建应用的 API Key（应用级），无管理权限
- **钉钉**：无企业应用配置权限

### 架构决策

对比了三种集成方案，最终选定 **方案二：轻量后端代理**：

```
Prodash 前端
    ↓
Node.js 后端（轻量代理）
    ↓
Dify Workflow API
    ↓
返回日报文本
```

理由：

- API Key 只存在后端环境变量，不暴露给前端
- 脱敏逻辑前后端双重执行
- 后续钉钉适配器可无缝接入，不重做日报生成

### Dify 应用类型

选定 **Workflow 应用**（非 Chatflow）：

- 输入结构固定、输出稳定
- 无需多轮对话或上下文记忆
- 接口：`POST /v1/workflows/run`

### 核心逻辑

**前端状态机（ReportView）：**

```
idle → preview → loading → success / error
```

- `idle`：填写补充内容
- `preview`：展示脱敏预览，用户确认后才能发起请求
- `loading`：请求中（禁止确认按钮，但保留输入）
- `success`：展示日报，支持复制
- `error`：显示错误提示，输入内容不丢失

**脱敏规则（前后端共用）：**

- 手机号 → `[手机号]`
- 邮箱 → `[邮箱]`
- 身份证号 → `[身份证号]`
- 带 token/access_token/secret/key 参数的 URL → `[敏感链接]`

**后端（Node.js 原生 HTTP）：**

- 接口：`POST /api/reports/daily`
- 256KB 请求体限制；日期字段校验；extraWork 字段限 5000 字符
- 服务端再次脱敏，不信任前端
- Dify 返回格式校验（`data.outputs.report` 或 `data.outputs.text`）
- 错误响应统一文案，不泄露 Dify 原始错误或 API Key
- 显式 Mock 模式（`DIFY_MOCK=true`），返回带 `[Mock]` 标记的固定日报

**Dify 客户端（difyClient）：**

- 真实模式调用 `${baseUrl}/v1/workflows/run`
- 请求体：`{ inputs, response_mode: 'blocking', user }`
- AbortController 超时控制
- 未配置 Key 时启动即报错，不返回 Mock 内容

### 环境配置

```env
DIFY_BASE_URL=http://dify.enwaysoft.com
DIFY_API_KEY=<应用级API-Key>
DIFY_USER=prodash
DIFY_TIMEOUT_MS=30000

```

## 五、集成测试与问题处理

### Dify API 地址问题

初始调用返回 `404`，原因：`DIFY_BASE_URL` 配置为 `http://dify.enwaysoft.com/v1/workflows/run`（完整接口路径），导致代码拼接后变成 `/v1/v1/workflows/run`。

修正：`DIFY_BASE_URL` 只填根地址 `http://dify.enwaysoft.com`，代码自动拼接 `/v1/workflows/run`。

### Dify Workflow 应用配置

在 Dify 中创建的 Workflow 应用需配置：

**开始节点输入变量（全部文本类型）：**

| 变量名 | 说明 |
|---|---|
| `report_date` | 日报日期 |
| `completed_tasks` | 已完成任务 JSON |
| `pending_tasks` | 未完成任务 JSON |
| `extra_work` | 补充工作 JSON |
| `risks` | 问题与风险 |
| `tomorrow_plan` | 明日计划 |

**结束节点输出变量：**

| 变量名 | 类型 | 值 |
|---|---|---|
| `report` | 字符串 | LLM 节点的输出 |

### 后端进程中断

本地后端进程在多次重启测试中因工具调度异常（ChildProcess.kill）反复被回收。每次需通过检查端口占用情况确认后端是否存活，再重新启动。

**最终状态：** 后端运行正常（pid=35728），前端代理正常，Dify Workflow API 返回 200，日报生成成功。

## 九、关键技术决策总结

| 决策点 | 选定方案 | 理由 |
|---|---|---|
| 集成架构 | 轻量后端代理 | 安全边界清晰，API Key 不暴露 |
| Dify 应用类型 | Workflow | 输入输出固定，无需多轮对话 |
| 脱敏策略 | 前后端双重执行 | 不信任任何单侧 |
| 数据日期口径 | `createdAt` 筛选 | 现有模型无 `completedAt`，已在界面明确说明 |
| Mock 策略 | 显式 `DIFY_MOCK=true` | 区分真/假结果，防止误用 |
| 分支策略 | Git Worktree 隔离 | 保护主分支，完成后可选择性合并 |
