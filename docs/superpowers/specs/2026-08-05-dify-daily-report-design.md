# Dify 工作日报助手设计文档

- 日期：2026-08-05
- 状态：已获用户逐节确认
- 项目：Prodash

## 1. 背景与目标

Prodash 当前是一个 React + Vite 的个人效率工作台，待办数据保存在浏览器 `localStorage`，尚无后端、账号体系或数据库。目标是先实现“工作日报助手”，后续再扩展到钉钉自动发送。

本期用户场景：用户在 Prodash 中查看当天待办，补充临时工作、会议、问题和明日计划，由公司私有化部署的 Dify 生成结构稳定、适合发送给直属领导的中文日报。

## 2. 范围

### 本期包含

- 新增“日报”功能入口
- 自动读取指定日期的 Prodash 待办
- 分别整理已完成和未完成任务
- 提供补充工作内容输入：临时工作、会议、问题与风险、明日计划
- 发送前展示脱敏预览
- 自动识别并替换常见敏感信息：手机号、邮箱、身份证号、可能含令牌的敏感链接
- 用户确认后调用后端日报接口
- 后端调用公司私有化 Dify
- 在 Prodash 展示固定结构的 AI 日报
- 支持复制日报文本，便于当前阶段手动发送到钉钉私聊

### 本期不包含

- 钉钉企业内部应用、机器人或自动发送
- 团队协作、多人账号和云端任务同步
- 将全部历史任务上传给 Dify
- 将 Dify API Key 放在前端
- 自动保存补充工作内容

### 后续扩展

后端保留发送适配器边界，未来可增加钉钉私聊发送适配器，不重做日报生成能力。

## 3. 方案选择

### 方案一：前端直接调用 Dify

开发最快，但 API Key 会暴露在浏览器中，不适合公司内部应用，仅可用于临时演示。

### 方案二：轻量后端代理（采用）

Prodash 前端调用后端日报接口，后端执行脱敏、校验并使用环境变量中的 Dify API Key 调用 Dify。该方案安全边界清晰，并为后续钉钉适配器保留扩展点。代价是需要新增一个可被前端访问的 Node 服务。

### 方案三：先复制到 Dify 网页端

无需 API Key 或后端，适合权限申请期间的过渡，但人工步骤多，不是真正的自动助手。

本项目采用方案二；在拿到 Dify API Key 前，可用模拟响应验证前端交互。

## 4. 系统架构

```text
Prodash 前端
├── ReportView
│   ├── ReportDateSelector
│   ├── ReportSourceSummary
│   ├── ReportExtraInput
│   ├── PrivacyPreview
│   ├── GenerateReportButton
│   └── ReportResult
│
└── 日报 API 客户端
        ↓
轻量 Node 后端
├── 请求校验
├── 服务端脱敏
├── Dify 生成适配器
└── 未来：钉钉发送适配器
        ↓
公司私有化 Dify
```

前端继续读取现有 `prodash.todos.v1`，不改变现有待办数据模型。后端部署位置暂时抽象为公司允许的 Node 服务；开发阶段可本地运行，后续再根据公司环境部署。

## 5. 前端组件与职责

新增日报视图，职责如下：

- `ReportView`：协调日期、输入、脱敏、请求和结果状态
- `ReportDateSelector`：默认选择当天，允许选择需要生成的日期
- `ReportSourceSummary`：展示将被汇总的完成/未完成任务数量
- `ReportExtraInput`：收集临时工作、会议、问题与风险、明日计划
- `PrivacyPreview`：展示脱敏后的提交内容，要求用户确认
- `ReportResult`：展示日报、重新生成和复制操作

前端不保存补充工作内容，不处理 Dify API Key。

## 6. API 契约与数据流

### 请求

```http
POST /api/reports/daily
Content-Type: application/json
```

```json
{
  "date": "2026-08-05",
  "completedTodos": [],
  "pendingTodos": [],
  "extraWork": {
    "temporaryWork": "",
    "meetings": "",
    "risks": "",
    "tomorrowPlan": ""
  },
  "clientSanitized": true
}
```

### 后端处理

1. 校验字段、日期和文本长度。
2. 再次执行服务端脱敏，不能只信任前端。
3. 组装 Dify 工作流变量。
4. 使用环境变量中的 Dify API Key 调用 Dify。
5. 设置超时并校验 Dify 返回格式。
6. 不记录完整日报请求日志。

### Dify 输入变量

- `report_date`
- `completed_tasks`
- `pending_tasks`
- `extra_work`
- `risks`
- `tomorrow_plan`

### 响应

```json
{
  "report": "生成的日报文本",
  "generatedAt": "2026-08-05T18:00:00Z"
}
```

数据流为：本地待办与补充内容 → 前端脱敏预览 → 用户确认 → 后端再次脱敏与校验 → Dify → 日报文本 → Prodash 展示与复制。

## 7. 日报格式与 Dify 约束

日报固定包含以下结构：

1. 今日完成
2. 进行中/未完成
3. 补充工作
4. 问题与风险
5. 明日计划

Dify 提示词要求：

- 使用固定日报结构
- 不编造未提供的事实
- 空字段输出“无”或省略
- 语言简洁、正式，适合发送给直属领导
- 不输出敏感信息
- 只返回日报正文，不返回额外解释

## 8. 隐私与脱敏

第一版采用“自动识别 + 用户确认”。常见敏感信息替换为：

- 手机号 → `[手机号]`
- 邮箱 → `[邮箱]`
- 身份证号 → `[身份证号]`
- 可能含访问令牌的 URL → `[敏感链接]`

脱敏预览确认是调用接口的前置条件。自动脱敏不能识别所有公司机密，界面需提醒用户进行人工检查。后端必须再次脱敏。Dify API Key 只保存在后端环境变量中。

## 9. 错误处理

| 情况 | 处理 |
|---|---|
| 没有任务或补充内容 | 允许生成，使用可用内容 |
| 脱敏失败 | 阻止请求并提示检查内容 |
| 后端不可访问 | 提示服务暂不可用，保留输入 |
| Dify 超时 | 提示重试，不清空输入 |
| Dify 返回格式错误 | 提示生成失败，不展示不完整结果 |
| Dify API Key 无效 | 后端记录技术错误，前端显示通用提示 |
| 复制失败 | 提供手动选中文本的备用方式 |

任何失败都不得清空用户填写的补充内容。

## 10. 测试与验收

### 前端测试

- 正确筛选指定日期的任务
- 完成和未完成任务进入正确区域
- 补充内容正确提交
- 手机号、邮箱等内容正确脱敏
- 未确认脱敏预览时不能生成
- 成功响应正确展示日报
- 请求失败后输入内容仍保留

### 后端测试

- 请求字段和文本长度校验
- 服务端再次脱敏
- Dify 请求参数映射
- API Key 不出现在响应或日志中
- 超时、错误状态码和异常响应处理
- Dify 返回结果格式校验

### 手动验收

用户可以选择日期、补充工作内容，确认脱敏预览后生成结构稳定的日报，并复制结果。Dify 不可用时，输入内容不丢失并显示明确错误提示。当前没有钉钉权限时，可复制结果手动发送到本人钉钉私聊。

## 11. 未来钉钉集成

拿到企业内部应用或机器人配置权限后，在后端增加钉钉私聊发送适配器：

```text
日报生成服务
├── Dify 生成适配器
└── 钉钉私聊发送适配器
```

日报生成、脱敏和前端展示无需重做；只需增加发送配置、发送状态和失败重试策略。
